# Convention: per-vendor model choices persist as vendor-scoped runtime.toml keys and apply on the next thread

**Rule.** When a vendor runtime exposes a model catalog, the user's model pick for that vendor is persisted as a **vendor-scoped key in `~/.agent-tui/runtime.toml`** (the shipped instance: `codex_model` for the Codex catalog loaded via `model/list`), alongside the runtime selection itself. The pick **applies on the next thread**, not mid-thread. Two moves are forbidden: inventing a second persistence location for a vendor's model choice, and hot-swapping the model inside an in-flight thread.

**Grounding.**
- `docs/LOCAL_CLI_AUTH.md`, "TUI usage (shipped)": "After `/runtime codex`, Agent TUI loads Codex `model/list` and **`/model` shows the Codex catalog**. Selection is stored in `~/.agent-tui/runtime.toml` (`codex_model`) and applied on the next thread."
- Same file: the vendor *runtime* choice is already persisted in `~/.agent-tui/runtime.toml` — the vendor-scoped model key co-locates the model pick with the runtime pick in the one file that owns cross-vendor selection state.

**Why:** vendor catalogs are loaded live from each runtime (`model/list` over the warm connection), so vendor model IDs are per-vendor state, not entries in one shared catalog — a vendor-scoped key (`codex_model`, and by extension `claude_model` when the Agent SDK bridge lands) keeps each vendor's pick independent and keeps `runtime.toml` the single file to read, script, or reset for all selection state. Thread-boundary application matters because a thread's turns ride one warm runtime connection with its own handshake and tool index; swapping the model mid-thread would either silently split a conversation across models or force a reconnect mid-turn.

**How to apply:** when wiring a model catalog for a new or newly-routable vendor, load the catalog from the vendor runtime's own listing call, persist the pick as `<vendor>_model` in `~/.agent-tui/runtime.toml`, and apply it at the next thread boundary — document exactly that phrasing in the user-facing table. When scripting or resetting a selection, edit `runtime.toml` rather than hunting for another config surface. When reviewing a vendor-catalog change, treat a new persistence file, an unscoped shared `model` key, or a mid-thread model swap as a defect against this convention. If a user reports "I picked a model and nothing changed," check first whether they are still in the pre-pick thread — the change lands on the next one.
