# Convention: Grok's pre-scheme arrangements are grandfathered, never precedent — new vendors follow the vendor-scoped scheme

**Rule.** Grok's departures from the vendor-scoped scheme — the built-in sampler catalog instead of a live-fetched vendor catalog, the absence of a `grok_model` key in `~/.agent-tui/runtime.toml`, Agent TUI-native OIDC/API-key auth instead of harness-reused login, sampler HTTP instead of a warm vendor runtime — are **grandfathered legacy**, not design options. A new or newly-extended vendor integration always follows the vendor-scoped scheme: one `<vendor>_model` key co-located with the runtime selection, a catalog fetched live from the vendor's own harness, auth reused from the vendor's CLI login, inference over a warm runtime connection. Citing Grok's shape as precedent for deviating from any of these is a defect in review.

**Grounding.**
- `suggested/wiki/runtime-toml-reference.md`: "Pattern for future vendors: one `<vendor>_model` key per catalog-shipped vendor, co-located with the runtime selection. Grok's model pick predates this file's vendor-scoped scheme and rides the built-in sampler catalog." — the reference states the pattern and the exception in the same breath.
- `suggested/wiki/vendor-runtime-readiness-ladder.md`: "a catalog is always served by the vendor's own local harness (live-fetched, never hardcoded)" — stated as a ladder rule with Grok listed separately as "the built-in default."
- `docs/LOCAL_CLI_AUTH.md`, runtime table: Claude and Codex both carry "**no Agent TUI OAuth**" while Grok alone uses the "Existing OIDC / API key" — the exception is confined to the one pre-scheme row.

**Why:** exceptions read as precedent to whoever finds them first. A developer wiring a fourth vendor who greps the codebase will find Grok's hardcoded catalog, its native auth, and its keyless model persistence before finding the convention docs — and each looks like a sanctioned pattern to copy. The scheme's guarantees (live catalogs never drift, `runtime.toml` is the single selection surface, credentials never cross the harness boundary) hold only for vendors on the scheme; copying the grandfathered shape silently forfeits them one vendor at a time.

**How to apply:** when reviewing a new vendor integration, check it against the vendor-scoped scheme, not against Grok. When a diff justifies a deviation with "Grok does it this way," reject with a pointer here. When Grok itself is eventually migrated onto the scheme (e.g. the open Grok model-pick persistence drift resolving to a `grok_model` key), update the legacy exception map and this doc in the same change.
