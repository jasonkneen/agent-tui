# Convention: one transport per vendor — the catalog rides the same connection the inference bridge uses (or will use), never a bespoke third path

**Rule.** A vendor runtime has exactly **one** connection shape across all rungs of the readiness ladder. The catalog query (rung 2) is wired into the same connection that serves — or, for a not-yet-routable vendor, *will* serve — inference turns (rung 3): Codex's catalog is `model/list` over the warm `codex app-server` connection that also routes turns; Claude's catalog rides the same `claude -p --output-format json` + sticky `--resume` harness its eventual Agent SDK bridge continues. Building a separate transport for the catalog — a one-shot HTTP call, a second subprocess flavor, a dedicated listing daemon — is a defect even if it returns correct models.

**Grounding.**
- `suggested/workflows/ship-catalog-rung-for-detect-only-vendor.md`, step 1: "Pick the catalog transport from the vendor's runtime shape... Do not invent a third shape — reuse whatever connection the eventual inference bridge will use."
- `suggested/agent-updates/vendor-model-catalogs-fetched-live.md`, How to apply: "wire the catalog query into that vendor's runtime pool (the same connection that serves turns), never a static list or a one-shot HTTP call."
- `suggested/wiki/warm-runtime-shapes-socket-vs-subprocess.md`: the two shipped shapes are enumerated as the complete set, with each vendor's catalog source listed on the same row as its turn transport.

**Why:** this is a distinct fact from the fetched-live rule. Fetched-live governs the catalog's *source* (the vendor's own runtime, never a hardcoded list); this convention governs its *transport identity*. A live-fetched catalog over a bespoke one-shot path would satisfy fetched-live and still be wrong: it creates a second connection lifecycle nobody maintains, it re-pays cold-start per catalog open, and at promote-time (rung 2 → rung 3) the catalog path would have to be rewired instead of already sharing the pool the bridge lights up. It also closes the same loophole the detection/inference split closes for turns — a one-shot catalog request built from detected credentials is the same forbidden shortcut in miniature.

**How to apply:** when shipping the catalog rung, route the listing call through the vendor's runtime pool/harness — the artifact the promote-to-routable workflow will later wire turns into. When reviewing, treat any second transport for a vendor (a `reqwest` call, an extra spawn shape, a separate listing process) as a defect regardless of what it fetches. When reading a vendor's row in the shipped table, expect one transport column to explain both its catalog and its turns.
