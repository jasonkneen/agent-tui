# Convention: a `<vendor>_model` key lands with the catalog rung — and the runtime.toml keyset is itself adjudication evidence

**Rule.** A vendor-scoped model key in `~/.agent-tui/runtime.toml` exists **only for catalog-shipped vendors**, and it is created in the same change that ships the vendor's catalog rung (ship-catalog-rung step 3: wire `/model` to the live catalog, persist the pick as `<vendor>_model`). Two moves are forbidden: pre-provisioning a key for a detect-only vendor whose catalog has not shipped, and shipping a catalog whose pick persists anywhere else. Because the keyset tracks the rung this tightly, the *absence* of a key is meaningful evidence in adjudication — for scheme-era vendors, no key means no catalog rung. Grok is the one grandfathered exception: its pick "predates this file's vendor-scoped scheme," so its missing `grok_model` key proves nothing about its rung — and where Grok's pick actually persists is a frozen TBD drift, so no doc may assert an answer until that row closes.

**Grounding.**
- `suggested/wiki/runtime-toml-reference.md`: "Pattern for future vendors: one `<vendor>_model` key per catalog-shipped vendor, co-located with the runtime selection."
- `suggested/workflows/ship-catalog-rung-for-detect-only-vendor.md`, step 3: "Persist the pick as a vendor-scoped `runtime.toml` key. Follow the shipped naming: `<vendor>_model` … applied on the next thread."
- The keyset already serves as evidence: the Grok model-pick persistence drift's Value B rests on "lists only `codex_model` and `claude_model` … no `grok_model` key exists."
- The shipped instances confirm the coupling: `codex_model` and `claude_model` each appeared exactly when that vendor's catalog shipped (Codex via `model/list`, Claude via the `claude -p` harness).

**Why:** the existing conventions say where a pick persists and how it applies, but not *when a key may exist at all*. Without that, a speculative `claude_model`-style key added ahead of a catalog would have silently poisoned the evidentiary read — the Grok drift registration leaned on the keyset being an honest record of which vendors reached rung 2. Same-change coupling (the workspace's general coupling law applied here) is what keeps the file readable as evidence: key present ⇔ catalog shipped, for every vendor that postdates the scheme.

**How to apply:** when shipping a catalog rung, add the `<vendor>_model` key in that change and nowhere earlier. When reviewing, treat a `<vendor>_model` key with no shipped catalog behind it as a defect — it is a false rung assertion in file form. When adjudicating a persistence or rung question, you may cite a scheme-era vendor's missing key as evidence of no catalog rung, but never cite Grok's missing key for anything: it is grandfathered, never precedent.
